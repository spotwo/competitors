# ADR 0014 - Inventory Key, Stock Dimensions, Merge/Split and PostgreSQL Position Model

Status: Proposed

Date: 2026-08-18

## Context

`InventoryPosition` is the low-latency current balance in the Spotwo inventory kernel, but its identity must be precise before table keys, indexes and locking can be designed. Treating every visible field as part of the key creates excessive cardinality and rewrite cost. Treating too few fields as identity silently merges stock that is not operationally fungible.

Vendor evidence shows several recurring patterns:

- SAP EWM quant identity combines physical placement/HU context with a stock key and can intentionally prevent addition to otherwise similar stock.
- Dynamics models explicit storage/tracking dimensions and allows reservations at different hierarchy granularities.
- Oracle inventory is addressed by a container or an active location and can have multiple inventory records in the same container/location.
- Oracle LPN inquiry separates container placement/status from the inventory lines and attributes held inside that LPN.
- SAP and Oracle model serial identity separately from the surrounding quantity record.
- SAP HUs can be nested, so copying every parent HU or resolved location into every contained stock key would create unnecessary write fan-out.

The Inventory Key therefore represents **fungibility and segregation**, not every attribute known about inventory.

## Proposed decision

### 1. Inventory Position uses a surrogate ID plus a semantic unique key

Use a stable surrogate `inventory_position.id` (UUIDv7 generated by the application) for references, ledger legs and events.

Separately enforce one live position per canonical Inventory Key with a database unique constraint.

The semantic key is:

```text
InventoryKey
  warehouse_id
  anchor
    exactly one of:
      location_id
      handling_unit_id
  item_id
  owner_id
  inventory_condition_id
  lot_id?                 # only when lot/batch controlled
  stock_scope_id?         # project / sales-order / consignment / special stock
  attribute_set_id?       # configured identity-affecting attributes
  stock_segment_id?       # explicit no-merge/provenance partition
```

`tenant_id` participates in the physical database unique constraint as a namespace and security boundary but is not itself a warehouse stock dimension.

### 2. Location and Handling Unit are one physical-anchor dimension

A position is physically anchored in exactly one immediate holder/address:

```text
Loose stock
  InventoryPosition -> Location

Contained stock
  InventoryPosition -> direct HandlingUnit
                           |
                           +-> parent HandlingUnit?
                           |
                           +-> Location when top-level
```

Do **not** require both `location_id` and `handling_unit_id` on one position.

Consequences:

- Moving a complete HU **within the same warehouse** changes HU placement/version and does not rewrite every contained Inventory Position.
- Repacking stock from HU A to HU B changes Inventory Anchor and therefore posts a real inventory movement/split.
- Nested stock references only the immediate containing HU. Parent HUs and resolved location are derived from the acyclic containment tree.
- `warehouse_id` remains explicit on the position for routing, partition/index locality and warehouse-level policy, and must agree with the resolved anchor warehouse.
- Moving an HU across a warehouse boundary is not the cheap same-warehouse relocation case. It follows Transfer / issue-and-receipt semantics and the destination stock belongs to new warehouse keys.
- A full-HU relocation must still produce durable HU movement/history and appropriate domain events even when no contained Inventory Position quantity leg changes.

### 3. Required stock dimensions

#### Item

`item_id` is always required. Product variants that are separate SKUs belong in item master identity rather than being repeated as arbitrary position fields.

#### Owner

`owner_id` is required. A single-owner warehouse still uses its canonical owner organization. This avoids nullable-owner uniqueness ambiguity and keeps the model ready for 3PL inventory.

`owner_id` is not intended to permanently collapse every entitlement concept. SAP evidence distinguishes owner from the party entitled to dispose, so a separate operational-entitlement/account dimension remains an explicit research question before adoption.

#### Inventory condition

`inventory_condition_id` is required and defaults to the warehouse's normal/unrestricted condition.

It represents a fungibility/stock-class distinction such as normal, damaged, inspection or quarantine when the condition makes quantities operationally non-equivalent.

Do not use this field for workflow states such as picked, packed, loaded or shipped.

### 4. Optional stock dimensions

#### Lot / batch

`lot_id` participates in the key only for lot-controlled stock. Different lots never merge merely because item/location/owner match.

Lot-level metadata such as manufacture or expiry date should normally live on the Lot. If the same lot can legally carry distinct identity-affecting local attributes, those differences use `attribute_set_id` or `stock_segment_id` rather than duplicating lot identity.

#### Stock Scope

`stock_scope_id` isolates otherwise identical stock with distinct business entitlement/purpose, for example project stock, sales-order stock, consignment or another special-stock class.

This is deliberately separate from quality condition and from customer ownership.

#### Inventory Attribute Set

`attribute_set_id` references an immutable, normalized set of configured identity-affecting attributes.

Examples may include grade, country of origin, regulated attributes, or expiry when expiry is not owned by Lot in the configured item model.

Do not put arbitrary JSON directly into the hot composite unique key. Store attributes in a canonical record with a stable fingerprint and reference its ID.

#### Stock Segment

`stock_segment_id` is an escape hatch for **intentional non-merging** when all ordinary dimensions match but stock provenance or policy must stay separate.

Examples:

- a warehouse forbids addition to existing stock,
- goods receipt date must remain operationally distinct,
- inspection/document provenance must stay separate,
- a certificate or source identity prevents commingling.

A segment is immutable. Normal fungible stock uses no segment.

### 5. Serial is not a generic Inventory Key column

Serial identity is individually tracked membership of a position:

```text
InventoryPosition qty = 10 EA
  +-- SerialMembership -> item X / serial 001
  +-- SerialMembership -> item X / serial 002
  ...
  +-- SerialMembership -> item X / serial 010
```

Candidate invariants:

1. One exact-tracked serial has at most one live physical position.
2. For an exact serial-controlled item, base-unit physical quantity equals live serial-membership count.
3. Serial identity includes item/product context; raw serial text is not assumed globally unique.
4. Moving a subset of serials moves those memberships with the corresponding quantity split.
5. Serial-level condition/status that differs from peers prevents aggregation unless represented separately in the serial model or through a different position key.

This avoids one mandatory Inventory Position row per serial while retaining exact serial location when the item policy requires it.

### 6. Fields that are NOT Inventory Key dimensions

The following do not identify a fungible stock position by themselves:

```text
physical_quantity
reserved_quantity
allocated_quantity
available_quantity
position_version
hold / lock
allocation eligibility
workflow state
entered UOM
base UOM
parent HU / top HU
resolved location of HU-contained stock
created_at / updated_at
receipt source reference
ledger transaction id
```

Rules:

- Quantities are mutable state of the position.
- Availability is derived.
- Reservations/allocations are commitments, not physical identity.
- Holds are restrictions/selectors over inventory, lot, HU, location or scope and do not create stock merely by existing.
- Quantity is normalized into the item's inventory/base UOM before posting; entered UOM remains ledger audit context.
- HU ancestors and resolved location are containment projections.

### 7. Merge rule

Two quantities may merge into one Inventory Position only when:

```text
all semantic Inventory Key dimensions are equal
AND item/warehouse commingling policy allows merge
AND serial/lot/attribute constraints remain valid
AND no explicit Stock Segment separation is required
```

If a target position with the same key already exists, posting adds quantity to that row atomically.

A merge does not destroy transaction history. Source provenance remains in ledger history and, where operationally necessary, in Stock Segment or other traceability records.

### 8. Split rule

A split occurs when part of a position is moved or transformed so that at least one identity dimension differs.

Examples:

```text
location A -> location B
HU A -> HU B
normal -> quarantine
owner A -> owner B
lot A -> lot B only through an explicit lot-identity transformation
scope A -> scope B
attribute set A -> attribute set B
segment A -> segment B
```

Posting semantics:

```text
source key       -Q
new/target key   +Q
```

For a conserving internal transformation the normalized physical net is zero.

If the entire quantity changes key, the old position may become zero and later be garbage-collected after all physical and commitment quantities are zero. Historical identity remains in the immutable ledger.

### 9. Lot and HU split/merge are different concepts

#### Stock position split/merge

Changes how quantity is distributed among Inventory Keys.

#### HU split/repack

Changes containment. It may create inventory movements when stock changes direct HU anchor.

A full-HU move within one warehouse does not alter contained stock anchors because the direct HU remains the same. Cross-warehouse movement is a transfer boundary and creates destination warehouse stock identity.

#### Lot split/merge

Changes traceability identity/genealogy and must be an explicit lot-domain operation. Ordinary stock merging never collapses different lot IDs.

## Candidate PostgreSQL model

This is a design target, not yet an application migration.

```sql
CREATE TABLE inventory_positions (
  id                     uuid PRIMARY KEY,
  tenant_id              uuid NOT NULL,
  warehouse_id           uuid NOT NULL,

  -- exactly one immediate physical anchor
  location_id            uuid,
  handling_unit_id       uuid,

  item_id                 uuid NOT NULL,
  owner_id                uuid NOT NULL,
  inventory_condition_id uuid NOT NULL,
  lot_id                  uuid,
  stock_scope_id          uuid,
  attribute_set_id        uuid,
  stock_segment_id        uuid,

  -- position-specific quantities only
  physical_qty            numeric(24, 6) NOT NULL DEFAULT 0,
  reserved_qty            numeric(24, 6) NOT NULL DEFAULT 0,
  allocated_qty           numeric(24, 6) NOT NULL DEFAULT 0,

  version                 bigint NOT NULL DEFAULT 0,
  updated_at              timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT inventory_position_one_anchor_ck
    CHECK ((location_id IS NULL) <> (handling_unit_id IS NULL)),

  CONSTRAINT inventory_position_nonnegative_ck
    CHECK (
      physical_qty >= 0
      AND reserved_qty >= 0
      AND allocated_qty >= 0
    ),

  CONSTRAINT inventory_position_commitment_bounds_ck
    CHECK (
      reserved_qty <= physical_qty
      AND allocated_qty <= physical_qty
    ),

  CONSTRAINT inventory_position_key_uq
    UNIQUE NULLS NOT DISTINCT (
      tenant_id,
      warehouse_id,
      location_id,
      handling_unit_id,
      item_id,
      owner_id,
      inventory_condition_id,
      lot_id,
      stock_scope_id,
      attribute_set_id,
      stock_segment_id
    )
);
```

`NULLS NOT DISTINCT` is important because nullable optional dimensions must still participate predictably in uniqueness. The target PostgreSQL version must support it.

`reserved_qty` and `allocated_qty` on this row represent only commitment already bound to this exact Inventory Position / Inventory Key. Coarse warehouse-, owner-, item- or hierarchy-level reservations remain separate commitment aggregates/projections until source specificity reaches this position. `reserved_qty` and `allocated_qty` are not assumed additive: an allocation may refine or overlap a previously reserved quantity according to the commitment model.

### Serial membership

```sql
CREATE TABLE inventory_serial_memberships (
  tenant_id   uuid NOT NULL,
  serial_id   uuid NOT NULL,
  position_id uuid NOT NULL REFERENCES inventory_positions(id),
  assigned_at timestamptz NOT NULL,

  PRIMARY KEY (tenant_id, serial_id)
);

CREATE INDEX inventory_serial_memberships_position_idx
  ON inventory_serial_memberships (tenant_id, position_id);
```

`serial_id` references a Serial master identity whose natural uniqueness is defined with item/product context.

### Handling-unit placement

Conceptually:

```sql
handling_units (
  id,
  tenant_id,
  warehouse_id,
  parent_handling_unit_id NULL,
  location_id NULL,
  version,
  ...
)
```

For a realized HU inside the warehouse, direct placement is normally one of:

```text
location_id set, parent_handling_unit_id null
OR
location_id null, parent_handling_unit_id set
```

Containment must be acyclic.

### Inventory Attribute Set

Candidate pattern:

```sql
inventory_attribute_sets (
  id,
  tenant_id,
  fingerprint,
  attributes jsonb,
  ...
)

UNIQUE (tenant_id, fingerprint)
```

JSON is acceptable behind an immutable deduplicated attribute-set identity. It is not the primary stock-row uniqueness mechanism.

## Candidate indexes

Start with the semantic unique constraint and evidence-driven operational indexes rather than indexing every dimension independently.

```sql
-- common availability/allocation candidate search
CREATE INDEX inventory_positions_item_warehouse_idx
  ON inventory_positions (
    tenant_id, warehouse_id, item_id, inventory_condition_id
  )
  INCLUDE (physical_qty, reserved_qty, allocated_qty, version);

-- loose stock by location
CREATE INDEX inventory_positions_location_idx
  ON inventory_positions (tenant_id, warehouse_id, location_id, item_id)
  WHERE location_id IS NOT NULL;

-- stock directly inside an HU
CREATE INDEX inventory_positions_hu_idx
  ON inventory_positions (tenant_id, warehouse_id, handling_unit_id, item_id)
  WHERE handling_unit_id IS NOT NULL;

-- lot traceability / FEFO candidate access
CREATE INDEX inventory_positions_lot_idx
  ON inventory_positions (tenant_id, item_id, lot_id, warehouse_id)
  WHERE lot_id IS NOT NULL;

-- 3PL owner-oriented inventory queries
CREATE INDEX inventory_positions_owner_idx
  ON inventory_positions (tenant_id, warehouse_id, owner_id, item_id);
```

Do not add indexes solely because a column exists. Confirm them with production query plans and cardinality.

## Locking granularity

### Normal quantity posting

Lock/version only the affected Inventory Position rows.

```text
lookup exact source/target key
  -> lock/version affected positions
  -> validate invariants
  -> append ledger legs
  -> update quantities
  -> commit
```

For a multi-position transaction, acquire row locks in deterministic position-ID/key order.

### Concurrent creation / merge

The semantic unique constraint is the final arbiter against duplicate position rows. Creation/merge logic must handle uniqueness races inside the posting transaction and retry boundedly where appropriate.

### Full Handling Unit movement

For same-warehouse relocation, lock/version the HU placement row. Do not lock or rewrite every contained Inventory Position when their direct anchor remains that HU and their quantities do not change. Persist HU movement/history and its outbox event through the HU movement boundary.

For cross-warehouse movement, use Transfer / issue-and-receipt semantics because `warehouse_id` changes and destination stock belongs to new Inventory Keys.

### Repack or partial HU movement

Lock the source position, destination position if it exists, and affected HU placement/membership records. Post normal source/target inventory legs.

### Serial movement

Lock serial membership plus affected position rows. Serial uniqueness is a correctness constraint, not merely an application-level check.

## Consequences

### Positive

- Position identity becomes mechanically defined.
- Same-warehouse full pallet/HU relocation avoids O(number of contained stock lines) position rewrites.
- 3PL owner segregation is first-class.
- Lot and serial tracking remain explicit without forcing one position per serial.
- Custom identity attributes are extensible without turning the hot unique index into JSON/EAV logic.
- Merge/split semantics map directly to ledger legs and row locks.
- PostgreSQL uniqueness can enforce one live row per fungible key.

### Costs

- HU-anchored inventory requires resolving location through containment for location-oriented queries.
- Cross-warehouse HU transfer still changes warehouse stock identity by design.
- Attribute-set canonicalization and fingerprinting need a strict contract.
- Stock Scope and Stock Segment add concepts that must remain narrowly defined to avoid becoming dumping grounds.
- Exact serial tracking requires membership-count consistency checks.

## Open questions

1. Should resolved HU location be computed on read, cached synchronously on HU, or maintained as a separate projection for high-volume location queries?
2. Which attribute names are permitted in identity-affecting Inventory Attribute Sets, and what canonical serialization/fingerprint algorithm is used?
3. Which special-stock types justify first-class Stock Scope subtypes in Spotwo?
4. How long should zero-balance Inventory Position rows remain before garbage collection?
5. Should high-contention pick faces default to `SELECT ... FOR UPDATE`, optimistic `version` retry, or choose policy per warehouse/process?
6. Do catch-weight items require a parallel authoritative quantity dimension in v1 or only audited secondary measure?
7. Should operational entitlement / party-entitled-to-dispose become a first-class key dimension separate from owner for 3PL and special-stock scenarios?
